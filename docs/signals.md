# Environment signal privacy register

This register defines the environment signals accepted by
`backend/app/schemas.py`. They are coarse, contextual signals for
deterministic rules, not a device fingerprint and not an identity system.

## Privacy classes

| Class | Meaning | Handling |
|---|---|---|
| C1 — low-sensitivity context | Coarse browser, platform, locale, display, or capability category | Collect only when needed for a rule; do not combine into an identifier. |
| C2 — derived integrity signal | A boolean result of a local integrity or automation check | Store the boolean outcome and rule explanation, never the inspected source text or function body. |
| C3 — server-side control | A request-level control result generated by the backend | Keep only for the request/rate-limit decision; do not use as a client fingerprint. |

## Behaviour and server controls

Environment signals are evaluated alongside aggregate behaviour values. The
behaviour payload may contain timing and event-trust aggregates needed by R11
and R12, but must not contain typed characters, key identities, raw input
content, or persistent identifiers. The backend may supply the following
request-level values:

- `rate_limit_exceeded`: server-side result for R13.
- `nonce_age_ms`: elapsed time from nonce issuance to an action.
- `invalid_nonce_or_signature`: hard validation result that bypasses model
  scoring.

These controls are request decisions, not client attributes.

## Explicitly prohibited

The environment layer must not collect, derive, or persist:

- Full User-Agent strings or raw Client-Hints headers after parsing.
- IP addresses as model features, stable device IDs, cookies, account IDs, or
  cross-request correlation IDs.
- Canvas, audio, font, or raw WebGL fingerprint hashes.
- Exact hardware identifiers, serial numbers, MAC addresses, or installed
  software lists.
- GPS coordinates, precise location, browsing history, page content, or form
  values.
- Typed characters, sentences, key identities, keystroke IDs, or clipboard
  contents.
- Raw function bodies, renderer strings, plugin names, or file paths.

No unique fingerprint hash is computed. Missing signals remain missing and
must not be silently replaced with suspicious values. Rule explanations may
be returned for debugging or policy decisions, but they must not include raw
payload values that the schema intentionally excludes.

## Retention and use boundary

Signals are intended for one assessment and its privacy-reviewed aggregate
audit record. The current project target is a local mock portal. Raw
environment payloads should not be retained beyond the approved experiment;
stored results should contain the rule IDs, score, reasons, model version, and
request correlation information only when that correlation is required by the
approved local workflow. This document does not authorize production
deployment or re-identification.

## Fixture coverage

The rule tests cover:

- A normal Chrome-on-Windows fixture with no fired rules and rule score `0`.
- A headless-browser fixture that fires multiple expected automation rules and
  produces a high rule score.
- One passing and one failing case for each R01-R13 rule.
